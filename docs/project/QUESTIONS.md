- Q126 (music data model): `packages/db/src/music.ts` and migration 0018 add works, score files, products (a score at a license tier, or a bundle), buyers, orders, licenses, downloads, commissions and newsletter subscribers. `music_items` (recordings and performances) gains an optional `work_id`. Default: one license per piece per order; a bundle is split across its pieces so the lines add up to the bundle price; a license allows 10 downloads (`download_limit`, owner can change per license). Lives in `packages/db/src/music.ts`.
- Q127 (rights): `@jerryqiu/scores` `canSell()` is the one rule: a piece is for sale only when published, and an arrangement of a copyrighted work only once "license on file" is ticked in the studio. Checked in the catalog, on the piece page and again when the order is made. Impact: if the owner wants a different rule, change `packages/scores/src/rights.ts`.
- Q128 (fees): Stripe's fee is passed to the buyer as its own line (`passThroughFee`: 2.9% + 30 cents), per Q56. Impact: change the constants in `packages/scores/src/pricing.ts` if the Stripe plan differs.
- Q129 (license wording): the license text in `packages/scores/src/license.ts` is a DRAFT for a lawyer to review (Q13). `TODO(owner):` lawyer review before any real sale. Three tiers (personal, ensemble, institution); prices are placeholders (Q61).
- Q130 (scores are watermarked per buyer): every delivered PDF gets a footer with the holder and license number on each page, a faint mark, and a license page at the end (pdf-lib, `stampScore`). Non-PDF files (MIDI, audio) are delivered as they are with a separate license PDF. The original file is never changed.
- Q131 (music payments): checkout uses Stripe Checkout (hosted page) through `@jerryqiu/payments` with `metadata[site]=music`; the photo webhook acknowledges and ignores events with that metadata, so both sites can share one Stripe account but each needs its own webhook endpoint. Without `STRIPE_SECRET_KEY` a development or preview build shows a labeled MOCK payment page; a production build refuses to take an order ("Payments are not open yet"). `TODO(owner): needs STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET on the music project.` Lives in `apps/music/src/lib/checkout.ts`.
- Q132 (order and newsletter links): the order link in a receipt and a subscriber's unsubscribe link are derived from the record id and `AUTH_SECRET` (HMAC), and only a hash is stored, so a receipt can always be re-sent with the same link. Impact: rotating `AUTH_SECRET` invalidates every order link (buyers use the library sign-in instead).
- Q133 (buyer library): no passwords. A one-time link (30 minutes) is emailed to an address that has a paid order; the answer on the form is the same for any address. The link opens a page with a button (mail scanners that open links cannot use it up). Session: signed cookie, 14 days.
- Q134 (recordings): embeds only, loaded on press of play; the id is validated per provider (`apps/music/src/lib/embed.ts`). Uploaded audio files are not played on the site yet. Practice audio and MIDI can be sold as score files.
- Q135 (CSV and sends): the newsletter send form requires typing the subscriber count and sends one message per subscriber through the email package (each logged in `email_log`); no scheduling or open tracking. A hidden field catches simple bots on the commission form. Public forms are rate limited per visitor (hashed address).
- Q136 (flying scope): the owner asked for the other sites after music (2026-10-27). Flying is rebuilt on Holominimal with the tools, a database-backed map and a studio; the background text, log entries and aircraft stay in the hub admin. Lives in `apps/flying`, `packages/aviation`, `packages/db/src/flying.ts` (migration 0020).
- Q137 (flight privacy, supersedes the mock source): see other-sites.md. A flight is shown only as a month, 7 full days after the landing day (the whole landing day counts), airport level, aircraft type only. `landed_on` is stored (the owner's own record) but never leaves the server. Impact if the owner wants a longer delay: `MIN_DELAY_DAYS` in `packages/aviation/src/flights.ts`.
- Q138 (tools are for learning): every tool carries the learning-only notice (`LearningNotice`), results show their working, and nothing claims to be a briefing or a navigation aid (Q36, Q49). The density altitude uses the 118.8 ft per degree rule of thumb; the weight and balance starts from SAMPLE numbers for an imaginary airplane; the reserve choices follow 14 CFR 91.151 (30 min day, 45 night VFR).
- Q139 (weather source): production builds read NOAA's Aviation Weather Center (no key; one request per lookup, 6 second timeout, answers over 6000 characters ignored, rate limited per visitor). Development and tests use labeled SAMPLE reports. `FLYING_WEATHER=off` switches the lookup off (paste only). The decoder lists tokens it does not understand instead of guessing.
- Q140 (trip tool inputs): headings are true (no variation or deviation), one wind is used for every leg, and the start/taxi/climb allowance is a fixed amount of fuel the pilot enters. Legs can be filled from two coordinate pairs (great circle). No airport database is bundled (Q54-style: the owner types what they use).
- Q141 (airports): the owner enters each airport once (code, name, coordinates) in the flying studio; the demo seed uses real coordinates for seven airports and SAMPLE flights.
- Q142 (forms): studio and public forms are submitted with onSubmit and a transition instead of `<form action>`, because React 19 resets the fields of an action-form after every submit, errors included, which threw away typed input (found by the make e2e). `ActionForm` (studio) and `useServerForm` (music public forms) are the pattern.
